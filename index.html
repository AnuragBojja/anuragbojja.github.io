🏗️ Multi-Layer IaC Architecture
Infrastructure as Code

Production Microservices Infrastructure — Multi-Layer IaC on Cloud

A production-grade AWS infrastructure built entirely from scratch using Terraform, designed as the foundational network and edge layer beneath a Kubernetes-based microservices platform. Every component was authored as reusable Terraform code, with state managed remotely in S3 and cross-layer resource references handled through AWS SSM Parameter Store to eliminate circular dependencies between layers.

  • Architected the complete cloud network foundation using custom reusable Terraform modules — provisioning a multi-AZ VPC with public, private, and database subnets, Internet Gateway, NAT Gateway with Elastic IP, and dynamically generated service-specific Security Groups where rule sets are decoupled from group creation to eliminate circular dependencies between service SGs.
  • Deployed the ingress and edge security layer with a public-facing Application Load Balancer, a wildcard AWS Certificate Manager certificate with automated Route53 DNS validation, and a CloudFront CDN with path-based cache behaviors for /media/* and /images/* — ensuring encrypted traffic at the edge with HTTPS enforcement.
  • Provisioned a private ECR container registry for internal image storage, eliminating any dependency on public registries like Docker Hub for the production platform.
  • Established a secure private administrative access layer with a hardened Bastion host in the public subnet and a self-hosted OpenVPN server allowing direct, encrypted developer-to-backend connectivity — providing an alternative to bastion-based access when developers need to interact with multiple backend resources.
  • Configured a VPC Peering connection between the platform VPC and a separate CI/CD (Jenkins) VPC — with route table updates and security group rules on both sides — enabling private cross-environment traffic without any public internet exposure for deployment traffic.
  • Managed all Terraform state remotely in S3 with cross-layer resource references decoupled through AWS SSM Parameter Store instead of terraform_remote_state, enabling independent and safe modification of any infrastructure layer without impacting the rest of the system.

Containers & Orchestration

Containerized Microservices Platform — Kubernetes Orchestration & Helm Packaging

End-to-end containerization and Kubernetes orchestration of a 10-service polyglot microservices platform — a complete container-native rebuild of the same RoboShop platform that runs on the Terraform IaC infrastructure. Every layer of the stack was built from scratch to production standards, from optimized Docker image building through production-grade Kubernetes manifests to reusable Helm chart packaging.

  • Built optimized Docker images for all 10 services (Node.js, Python, Java, MongoDB, MySQL, Redis, RabbitMQ) using multi-stage Alpine builds — installing build tooling only in the build stage, copying compiled artifacts into slim runtime stages, enforcing non-root user execution with explicit UID/GID assignment (typically UID 1001), and consolidating RUN instructions to reduce image layers.
  • Resolved six sequential errors during the Payment service Alpine migration — including the classic Alpine musl libc vs glibc mismatch for Python native dependencies, the correct semantics of --prefix vs --target for pip installs, and permission issues surfacing at UID 1001.
  • Authored production-grade Kubernetes manifests covering both stateless and stateful workloads — Deployments and ClusterIP Services for application layers with proper label selectors, StatefulSets with Headless Services and volumeClaimTemplates for databases (ordered pod creation, stable network identities), and HorizontalPodAutoscalers driving CPU-based traffic scaling on stateless workloads.
  • Provisioned persistent storage through an EBS-backed StorageClass with WaitForFirstConsumer binding mode — guaranteeing volumes are created in the same availability zone as the consuming pod to prevent cross-AZ scheduling issues in a multi-AZ cluster.
  • Mounted ConfigMaps two distinct ways: as bulk environment variables via envFrom for application configuration, and as file mounts via subPath for config files that must live at specific paths. Debugged a critical issue where Kubernetes auto-injected service link environment variables (enableServiceLinks: true) were silently overriding ConfigMap values — traced by deploying a custom debug container with network tools.
  • Implemented full role-based access control with dedicated ServiceAccounts, Roles, RoleBindings for namespace-scoped access, and ClusterRoles/ClusterRoleBindings for cluster-wide operations — with a multi-user access model separating an admin user (anurag) from a trainee user (keke) with restricted permissions.
  • Eliminated static AWS credentials in pods using IRSA (IAM Roles for Service Accounts) — Kubernetes ServiceAccounts trust AWS IAM Roles through OIDC federation, so pods assume roles at runtime via STS instead of having access keys mounted as secrets.
  • Exposed public traffic through the AWS ALB Ingress Controller (installed via Helm) with host and path-based routing rules to backend services, and configured liveness and readiness probes per service type — HTTP probes for web services, TCP socket probes for databases, with initial delay and failure thresholds tuned to actual startup behavior.
  • Packaged the entire platform as reusable Helm charts using Go templating and values-driven configuration — separate chart archetypes for Deployment services vs StatefulSet services — enabling any team member to install the full platform in a new environment with a single helm install command.

🚦 Security-Integrated CI/CD
CI/CD & Security

Automated CI/CD Pipeline — Security-Integrated Delivery on Kubernetes

An end-to-end CI/CD system that takes application code from a developer commit all the way to a deployed workload on a managed Kubernetes cluster — with security gates enforced at every stage where a real go/no-go decision is possible. Every piece of the pipeline is versioned, reusable, and secured against credential leakage. The whole system is designed around a single principle: nothing gets deployed unless it has passed every quality, security, and reliability check.

  • Jenkins Infrastructure (Terraform). The Jenkins controller, dedicated agent node, and SonarQube instance are all provisioned via Terraform in a dedicated Jenkins VPC (VPC-peered to the platform VPC). Each instance uses community-maintained AMIs, and all runtime configuration (Java runtime, Jenkins install, plugin bootstrap, SonarQube setup, credential seeding) is handled through automated userdata bash scripts — the same terraform apply recreates the entire delivery platform from scratch.
  • 8-Stage CI Pipeline. For each service, the pipeline runs eight sequential stages: version extraction → dependency installation → unit & functional testing → SonarQube static analysis with active quality gate polling (10-minute timeout, hard-fails on anything other than OK) → Dependabot vulnerability check via GitHub API → Docker build & ECR push with version-tagged artifacts → Trivy image scanning (fails on critical/high CVEs in the built image) → deployment trigger. Each stage is a real gate — there's no "warn and continue."
  • Least-Privilege Credentials. Every credential lives in Jenkins' native credentials store, referenced by name and never inlined in Jenkinsfiles or Groovy library code. Consistent naming: github-token, ssh-auth, aws-cred, sonar-token. Credentials are injected at the stage level using both environment { } blocks and step-level wrappers like withAWS(credentials: 'aws-cred') { } — each credential only present in the process environment for the specific stage that needs it, dramatically reducing blast radius.
  • Reusable Groovy Shared Library. All pipeline logic lives in a Groovy shared library under var/*. Two flagship files: nodejsEKSPipeline.groovy for the full 8-stage CI pipeline (with Maven variant for Java and Python variant in progress), and EKSDeploy.groovy for the CD pipeline. Each service repo contains only a thin Jenkinsfile that loads the shared library and calls the appropriate pipeline function — pipeline logic changes are made in exactly one place.
  • Multi-Language, Single Deployment Path. The CI pipelines are language-specific (Node.js, Java, Python), but the CD pipeline is unified: one EKSDeploy.groovy script deploys any service regardless of runtime — takes environment name and application version as inputs, then runs a two-stage deployment (create the target namespace if it doesn't exist, then deploy via Helm charts).

⚙️ VM Deployment Automation
Deployment Automation

VM-Based Production Deployment Automation — Terraform + Ansible IaC Pipeline

A production-grade VM-based (non-container) AWS platform. Application services are deployed and configured directly onto EC2 instances via Ansible rather than running as containers on Kubernetes. This is the previous generation of the same 10-service RoboShop platform — same application, different deployment model. Fully self-bootstrapping: one terraform apply on the bastion layer provisions the entire platform end-to-end.

  • Self-Bootstrapping Bastion. The Bastion host in the public subnet has a boot-time script that automatically triggers the terraform-aws-40-databases and terraform-aws-80-service layers on first boot — enabling fully hands-free provisioning of the entire platform from a single command.
  • Databases Layer. Provisions EC2 instances for each database (MongoDB, MySQL, Redis, RabbitMQ). Each instance configured via an Ansible role that installs the database software, applies initial configuration, and starts the service through systemd.
  • Ansible Role Architecture. One role per service (10 total: MongoDB, Redis, MySQL, RabbitMQ, Catalogue Node.js, User Node.js, Cart Node.js, Shipping Java, Payment Python, Frontend Nginx). A shared common role — imported via meta/main.yaml role dependencies — handles user creation, artifact download, runtime installation, and systemd unit management. Zero code duplication across the 10 roles.
  • Runtime Secrets via SSM. All secrets (SSH passwords, database root credentials) pulled at runtime from AWS SSM Parameter Store through the amazon.aws.aws_ssm lookup plugin — no credentials in playbooks or version control. All systemd unit files and Nginx configurations rendered from Jinja2 templates at deploy time.
  • Per-Service Deployment Pipeline. The 80-services layer uses a custom Terraform module invoked in a for_each loop over all services. For each service, the module runs: EC2 provisioning → Ansible role execution → instance stop → AMI baking → Launch Template creation → Target Group with health checks → Auto Scaling Group with rolling deployment strategy → CPU-based auto-scaling policy → ALB Listener Rule registration.
  • Backend + Frontend ALBs. Internal (private) ALB routes traffic between backend services within the private subnets. Public-facing frontend ALB in the public subnets handles end-user traffic.
  • Edge Layer. Wildcard ACM certificate with automated Route53 DNS validation. CloudFront in front of the frontend ALB with cache behaviors on /media/* and /images/* paths, HTTPS-only via the ACM cert.

Multi-Cloud

Multi-Cloud Deployment Strategy — IaaS vs PaaS Architecture

A full-stack Django web application deployed simultaneously across AWS (IaaS approach) and Azure (PaaS approach) with a shared Azure MySQL backend database. The multi-cloud architecture is a deliberate resilience decision — it reduces dependency on any single cloud provider and improves disaster recovery posture against regional outages, provider-level service degradations, and vendor lock-in risks.

  • IaaS Path (AWS EC2). Manual server configuration — Nginx as reverse proxy, Gunicorn as WSGI server, systemd for service management, and TLS certificates provisioned via Certbot/Let's Encrypt.
  • PaaS Path (Azure Web App). Managed platform deployment with Azure's built-in scaling, monitoring, and runtime management.
  • Shared Backend. Both deployments use the same Azure MySQL Flexible Server — single source of truth for application data across clouds.
  • CI/CD. GitHub Actions workflows trigger on push to main — no manual deployment steps.
  • Security Posture. IAM roles and Security Groups restrict database and application access. No public database exposure. TLS enforced end-to-end across both cloud environments.
