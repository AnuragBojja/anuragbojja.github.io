### 🏗️ Project 1: Production Microservices Infrastructure — 10-Layer IaC Architecture

**Stack:** Terraform · Ansible · AWS (VPC, IGW, NAT, Subnets, Security Groups, EC2, ALB, ASG, CloudFront, ACM, OpenVPN) · Route53 · SSM Parameter Store · Jinja2

**Overview:**

A fully automated, production-grade AWS environment for a 10-service polyglot microservices platform, built from the ground up across 10 independently state-managed Terraform layers. Every component — from the underlying VPC to the CDN distribution at the edge — is defined as code, with configuration management layered on top through Ansible roles.

**Network Foundation (Built from Scratch):**

Designed the entire AWS network foundation with production-level isolation. This included the VPC itself, public and private subnets distributed across multiple availability zones, database-tier subnets, Internet Gateway for public traffic, NAT Gateway for private-subnet egress, and route tables scoped per subnet tier. On top of this, provisioned 14 service-specific Security Groups — one per workload — with all ingress and egress rules deliberately separated into their own Terraform layer to eliminate circular dependencies and enforce least-privilege at the network level.

**Private Network Access via OpenVPN:**

To eliminate the risk of exposing SSH or internal service endpoints to the public internet, deployed an OpenVPN server within the VPC as a secure jump point. Engineers and CI/CD systems authenticate through the VPN before accessing anything private — meaning database subnets, internal ALBs, and backend services have zero direct public exposure.

**Custom Reusable Terraform Modules:**

Rather than writing one-off resource blocks, authored three custom Terraform modules that become the platform's building blocks:

- **VPC Module** — Provisions the entire network layer with configurable CIDR blocks, AZ distribution, and subnet tiers.
- **Security Group Module** — Outputs SG IDs to SSM Parameter Store, allowing downstream layers to reference them without hardcoding.
- **Service Configuration Module** — The most complex module, which handles the entire service deployment lifecycle end-to-end: EC2 provisioning, Ansible-based configuration, AMI baking, Launch Template creation, Auto Scaling Group with rolling refresh strategy, ALB Target Group registration, ALB Listener Rule attachment, and CPU-based Target Tracking scaling policies.

**6 Services, One Loop:**

All 6 application services are deployed through a single parameterized module invocation. Adding a new service to the platform is a matter of adding one entry to a variable map — no new code required.

**Public Endpoint Hardening:**

Deployed a public-facing ALB with a wildcard ACM certificate and TLS 1.3 enforcement, fronted by a CloudFront distribution with intelligent caching rules — static assets cached aggressively, API traffic passed through with minimal overhead. This gives the platform both global performance and full edge encryption.

**Ansible Configuration Layer:**

On top of the infrastructure, Ansible provides service-level configuration through a role-based architecture. Every service pulls secrets (database passwords, service credentials, API keys) from AWS SSM Parameter Store at runtime using the `amazon.aws.aws_ssm` lookup plugin — meaning credentials are never written to playbooks, version control, or environment files. All systemd unit files and Nginx configurations are rendered dynamically from Jinja2 templates, eliminating configuration drift across environments. One parameterized Ansible command deploys any of 10 services with zero code duplication.

**Cross-Layer State Decoupling via SSM:**

Rather than using Terraform's `terraform_remote_state` to read outputs across layers (which creates tight coupling), every layer writes its outputs to AWS SSM Parameter Store. Downstream layers read from SSM at plan time through `locals.tf`. This means teams can modify any layer independently without risking the rest of the system, and the entire architecture stays flexible as it evolves.

### 🐳 Project 2: Containerized Microservices Platform — Kubernetes Orchestration & Helm Packaging

**Stack:** Docker · Kubernetes · Helm · kubectl · Alpine Linux · ConfigMaps · StatefulSets · HPA · PV/PVC · StorageClass · RBAC · IRSA/OIDC · AWS ALB Ingress Controller

**Overview:**

Containerized and orchestrated the same 10-service polyglot microservices platform on Kubernetes — building everything from optimized Docker images through full production-grade manifests to reusable Helm charts. This project represents the container-native evolution of the same workload deployed via Terraform + Ansible, giving me the ability to compare and understand two fundamentally different deployment paradigms deeply.

**Docker Image Optimization:**

Built optimized Docker images for all 10 services (Node.js, Python, Java, MongoDB, MySQL, Redis, RabbitMQ) using multi-stage builds on Alpine base images. Build tooling — compilers, dev dependencies, package caches — lives only in the build stage and is discarded before the final runtime image is assembled. Every image enforces non-root user execution with explicit UID/GID assignments, prevents privilege escalation, and consolidates commands into single layers where possible to keep image size minimal.

The Payment service (Python/uWSGI on Alpine) required especially careful debugging — traced six sequential build errors involving Alpine's musl libc, missing kernel headers, and pip installation paths, ultimately resolving them by switching from `pip --target` to `pip --prefix` and installing the exact system libraries required.

**Full Production Kubernetes Manifests:**

Authored complete Kubernetes manifests from scratch — not just Deployments, but every resource type production workloads actually need:

- **Deployments** for stateless application services with configured resource requests and limits
- **ClusterIP Services** for internal service-to-service DNS resolution
- **StatefulSets** for stateful databases (MongoDB, MySQL, Redis, RabbitMQ) with stable pod identities
- **Headless Services** (clusterIP: None) paired with StatefulSets for direct pod-to-pod discovery
- **volumeClaimTemplates** to give each StatefulSet replica its own dedicated PersistentVolume
- **EBS-backed StorageClass** with `WaitForFirstConsumer` binding mode, ensuring EBS volumes are provisioned in the correct availability zone
- **ConfigMaps** used both as environment variables via `envFrom` and as mounted files via `subPath` — including debugging a subtle Kubernetes behavior where auto-injected service link environment variables silently override ConfigMap values (fixed by configuring `enableServiceLinks: false`)
- **HorizontalPodAutoscalers** with CPU-based scaling thresholds tuned per service
- **Liveness and readiness probes** using HTTP and TCP socket checks with per-service thresholds

**Public Traffic via AWS ALB Ingress Controller:**

Rather than using basic LoadBalancer services, installed and configured the AWS Load Balancer Controller inside the cluster, which enables native Ingress resources to provision real AWS Application Load Balancers with host-based and path-based routing rules. This means the platform exposes a single ALB to the internet, with intelligent routing distributing traffic to different backend Services based on the request URL — the same architectural pattern used in real production Kubernetes deployments at scale.

**Cluster Security via RBAC and IRSA:**

Implemented Kubernetes RBAC to enforce granular access controls: dedicated ServiceAccounts per workload, Roles for namespace-scoped permissions, ClusterRoles for cross-namespace and cluster-level operations, and both RoleBindings and ClusterRoleBindings tying identities to permissions. Also configured the `aws-auth` ConfigMap to map AWS IAM identities to Kubernetes usernames and groups — implementing real-world multi-user access control at the platform level.

For pod-to-AWS-service authentication, implemented IRSA (IAM Roles for Service Accounts) using the cluster's OIDC provider. Pods present signed JWT tokens to AWS STS, which verifies the token signature against the OIDC provider's public keys and issues temporary AWS credentials with automatic rotation — completely eliminating static IAM keys from container images and manifests.

**Helm Packaging with Values-Driven Templating:**

Packaged the entire platform as reusable Helm charts using Go templating and hierarchical `values.yaml` configuration. Built two chart archetypes — one for Deployment-type services and one for StatefulSet-type services — with the specific service configuration abstracted out to values files. This means installing the entire platform in a new environment (dev, staging, production) becomes a single `helm install` command with the appropriate values file, enabling true infrastructure repeatability and eliminating configuration drift.

### ☁️ Project 3: Multi-Cloud Deployment Strategy — IaaS vs PaaS Architecture

**Stack:** Django · AWS EC2 · Azure Web App · MySQL · Nginx · Gunicorn · GitHub Actions · TLS/SSL · IAM

**Overview:**

Deployed a full-stack Django application across two cloud providers simultaneously — AWS as an Infrastructure-as-a-Service (IaaS) deployment and Azure as a Platform-as-a-Service (PaaS) deployment — connected to a shared MySQL backend database. This was a deliberate multi-cloud architecture decision, not a hobby comparison: the goal was to reduce single-provider dependency and improve disaster recovery posture against regional outages, provider-level service degradations, and vendor lock-in risks.

**AWS IaaS Deployment:**

Provisioned a bare EC2 instance and hand-configured the entire application stack — installing Python, setting up virtual environments, configuring Nginx as the reverse proxy, running Gunicorn as the WSGI application server, managing the application lifecycle through systemd, and provisioning TLS certificates via Certbot/Let's Encrypt with automatic renewal. Access is controlled through IAM-scoped permissions and network-level Security Groups.

**Azure PaaS Deployment:**

Deployed the same application to Azure Web App, letting the platform handle runtime management, scaling, and TLS termination. This gave me a direct side-by-side comparison of how much operational overhead PaaS eliminates versus the control IaaS provides — a real trade-off analysis rooted in actual deployment experience rather than theory.

**Automated CI/CD:**

Both deployments are tied to GitHub Actions workflows that automatically build, test, and deploy on push to the main branch. This means the multi-cloud posture is maintained continuously — every code change ships to both providers without manual intervention.

**Security Hardening:**

Neither cloud environment exposes internal services to the public internet. The MySQL database is accessible only through internal network policies from both application deployments, IAM roles enforce least-privilege access, TLS is terminated at the edge on both sides, and no credentials are stored in application code or configuration files.

**Full Tools & Resources List:**
- **Web Framework:** Django
- **AWS (IaaS side):** EC2, IAM roles, Security Groups, Nginx reverse proxy, Gunicorn WSGI, systemd, Certbot/Let's Encrypt
- **Azure (PaaS side):** Azure Web App with built-in scaling and TLS
- **Database:** MySQL (shared across both cloud environments)
- **CI/CD:** GitHub Actions with automated build, test, and deploy workflows
- **Security:** TLS termination, IAM-scoped access, network policies, no public database exposure
